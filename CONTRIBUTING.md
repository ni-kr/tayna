# Contributing to tayna

Thanks for your interest in the project.

## 1. Pull requests

- The test suite must remain green, and new behaviour must be covered by tests.
- Public items need documentation (`missing_docs = "deny"`).
- `unsafe` code is rejected by the compiler (`unsafe_code = "forbid"`).
- The library must not panic. `clippy::unwrap_used`, `clippy::expect_used`, and
  `clippy::panic` are denied outside test builds in `src/lib.rs`.
- Warnings are errors in CI (`-D warnings`), which includes `clippy::pedantic`
  and `missing_debug_implementations`.
- A change to `Cargo.toml` needs the matching `Cargo.lock` update in the same
  pull request, because CI builds with `--locked`.
- The minumum supported Rust version (MSRV) is 1.85.0. Raising it means updating
  `rust-version` in `Cargo.toml` and the `msrv` matrix in
  .github/workflows/check.yml.
- Some CI jobs track thing outside this repository such as the beta and nightly
  compilers and newer dependency versions. They can fail for reasons unrelated
  to the change under review and are not required status checks.
- Pull requests are rebased onto `main`, so every commit is preserved. The
  branch must be tidy, with each commit self-contained and following the format
  in section 2.

## 2. Commit messages and releases

Releases are automated. When a relevant change lands on `main`, release tooling
determines the next version, publishes it to crates.io, and creates a Git tag.
No manual version assignment or `cargo publish` is needed.

Two independent rules determine the release:

- Whether a release happens depends on whether the change modifies a file
  included in the published crate.
- Which version is released depends on the commit messages.

### 2.1 What triggers a release

A release is triggered only when a change affects a file included in the
published crate. The exact file list is available with `cargo package --list`.

Changes limited to files outside the package, such as workflow files or this
document, do not trigger a release.

### 2.2 Commit message format

Version bumps follow [Conventional Commits](https://www.conventionalcommits.org):

```
<type>[optional scope]: <description>

[optional body]

[optional footer]
```

Once a release is triggered, the commit messages determine the version bump:

| Type | Version bump |
| --- | --- |
| `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `ci:`, `style:`, `perf:`, or an unrecognised type | Patch |
| `feat:` | Minor, except on `0.x`, where it bumps the **patch** |
| `feat!:` or a `BREAKING CHANGE:` footer | Major, except on `0.x`, where it bumps the **minor** |

For example:

- `fix:` changes `0.1.0` to `0.1.1`.
- `feat:` changes `1.0.0` to `1.1.0`, or `0.1.0` to `0.1.1`.
- `feat!:` changes `1.0.0` to `2.0.0`, or `0.1.0` to `0.2.0`.

The `0.x` version range is treated as unstable: backward-compatible features
bump the patch, while breaking changes bump the minor. Starting at `1.0.0`,
backward-compatible features bump the minor and breaking changes bump the major.
Following Conventional Commits ensures that the intended bump is recognised.

Unrecognised messages such as `fixed stuff` still trigger the corresponding
release when a packaged file changes. They default to a patch bump.

### 2.3 A note on breaking changes

Before proposing a version, the release tooling runs cargo-semver-checks against
the published crate to compare the public API. If a commit message understates a
breaking change, the proposed version bump is corrected. The same check runs on
pull requests, catching API compatibility issues before a release is prepared.

The check only corrects understatements. It cannot reduce an unnecessarily large
bump. A `feat!:` commit still triggers a breaking-change bump even when the API
remains backward-compatible.

## 3. The release process

1. A pull request is merged into `main`.
2. A bot opens a pull request titled `chore: release vX.Y.Z`. Its entire diff is
   the version bump in `Cargo.toml` and `Cargo.lock`.
3. Because that pull request is opened by automation, its CI runs start in an
   approval-required state. A maintainer selects "Approve workflows to run" in
   the merge box to release them. Until approval, required status checks remain
   pending. This is expected behaviour, not a CI failure.
4. Merging that release pull request publishes the crate to crates.io, creates
   the `vX.Y.Z` git tag, and creates a GitHub Release.

There is no `CHANGELOG.md` in this repository by design. Release notes are
generated by GitHub from merged pull requests and published on the
[Releases page](https://github.com/ni-kr/tayna/releases).

## 4. Running checks locally

CI runs these checks automatically, but running them locally can catch issues
sooner. These mirror what the `check`, `test`, and `security` workflows run:

```sh
# Formatting.
cargo fmt --check

# Lints, with warnings denied.
cargo clippy --locked --all-features --all-targets -- -D warnings

# Test suite. `--all-targets` excludes doc-tests, so they run separately.
cargo test --locked --all-features --all-targets
cargo test --locked --all-features --doc

# Public API compatibility against tge version published on crates.io.
cargo install cargo-semver-checks --locked
cargo semver-checks

# Documentation. CI runs `cargo docs-rs` on nightly to reproduce the docs.rs
# build. This is the stable approximation.
RUSTDOCFLAGS="-D warnings" cargo doc --locked --all-features --no-deps

# Every combination of features, all of which must compile.
cargo install cargo-hack --locked
cargo hack --feature-powerset check

# The minimum supported Rust version.
rustup toolchain install 1.85.0
cargo +1.85.0 check --locked --all-features

# Dependency advisories, licenses, and sources
cargo install cargo-deny --locked
cargo deny --all-features --config .config/deny.toml check
```

The macOS and Windows test runs, the minimal and updated dependency resolutions,
and the coverage report are left to CI.
